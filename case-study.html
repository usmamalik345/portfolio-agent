Agent Receptionist

A tool-calling LLM agent for appointment-based businesses, built as an engineering exercise in making an agent predictable: cited answers, guarded output, a deterministic fallback, and latency and cost I can measure.

Problem

Appointment businesses need answers that are fast and correct, not just fluent.

A front-desk agent for a hotel or a dental practice is a small, high-stakes domain. A wrong opening hour, an invented service, or a casual reply to an emergency is worse than no answer. A plain "LLM plus prompt" can do all three.

I built Agent Receptionist to see how far an LLM agent can be pushed toward reliable behaviour: ground answers in the business's own documents and cite them, handle the predictable cases without the model at all, check every sentence before it reaches the user, keep a deterministic path for booking, and measure latency and cost instead of guessing.

The two demo businesses, a hotel and a dental practice, are fictional. They exist to exercise the same engine against different documents, hours, and policies. Switch between them with ?biz=hotel and ?biz=dental.

Architecture

Cheap, deterministic decisions come first. The model is called only when it is needed, and its output is checked before it streams.

Reliability & guardrails

Layers around the model, each cheaper and more predictable than the model itself.

Before the model

Policy pre-routing

Emergencies, opening hours, and handoff to a human are decided by policy, not by the LLM. These cases cost zero tokens and behave the same every time.

Grounding

RAG that cites sources

Answers come from the business's own documents and carry their sources, so a reader can check where a claim came from instead of trusting the model.

After the model

Per-sentence guard

  • Entity allowlist: names and services must be known to the business.
  • Hours: stated times are checked against the real schedule.
  • Required facts: answers that must contain a fact are checked for it.

Fallback

Deterministic booking engine

Booking does not have to depend on model behaviour. A deterministic engine is kept as the fallback path, so the agent is not the only thing standing between a user and a booking.

Security

Secrets and errors stay server-side

  • No provider secrets in the client.
  • Raw provider errors are kept server-side and are not shown to users.

Delivery

Streaming and visibility

Replies stream over SSE with real token streaming, and a latency and cost panel makes each question's timing and token usage visible rather than assumed.

Tradeoffs & what I'd improve

What this design gives up, and what I would do next.

Tradeoffs

Predictability over flexibility

  • Policy routing and the guard make behaviour checkable, but they limit how freely the agent can phrase or improvise.
  • Allowlists and fact checks need maintaining per business as documents change.
  • A deterministic fallback adds a second code path to keep correct.

Next

What I'd improve

  • Fix the narrow eval regex and make live checks less brittle than pattern matching.
  • Larger live suites and repeated latency runs, instead of one live check.
  • Test on real business documents, not only the two fictional ones.
